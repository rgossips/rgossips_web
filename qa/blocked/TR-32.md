# TR-32 — Fallback, Failover & Degraded-Mode Testing  [BLOCKED — nothing to test]

**Objective.** Verify that when a primary provider is unavailable the platform
either fails over to a secondary without duplicating money or identity state, or
degrades to a defined mode — and that the switch is safe in both directions.

## Blocker — different in kind from the others

This is not blocked by the environment. It is blocked because **no fallback
exists**. Appendix F is a set of build recommendations, not a description of the
system. Today:

- **OTP delivery** — one provider (WhatsApp Cloud API). No SMS fallback. An
  outage stops every signup and every sign-in on all three surfaces.
- **Transactional email** — one shared-hosting SMTP relay. No secondary sender.
- **Escrow funding** — one gateway. Subscriptions have two; escrow does not, so
  a gateway outage blocks every deal from being funded.
- **Identity/GSTIN lookup** — one vendor, in the signup critical path.
- **Instagram auth** — no substitute exists, and the strategy is explicit that
  the fallback there is a product decision (phone-first signup with deferred
  social connection), not an integration.

The strategy's warning applies in reverse here: "A fallback that has never been
exercised is indistinguishable from no fallback." There is no fallback at all,
so there is nothing to exercise. Writing tests now would produce a suite that
passes vacuously.

## Unblocks when

A fallback is built. Appendix F's two P0 items:

1. **OTP SMS fallback** — MSG91, Kaleyra or Gupshup. All require TRAI DLT
   registration and template approval, which takes days to weeks. Register
   before it is needed; provisioning during an outage is too late.
2. **Transactional email** — SES, Brevo, ZeptoMail, Postmark or Resend, ideally
   as primary with SMTP as fallback. Publish SPF/DKIM/DMARC covering **both**
   senders before switching, or failing over pushes mail into spam.

## Spec to write, once one exists

A-61 to A-68. The three easiest to get wrong:

- **A-62 cross-provider idempotency.** One idempotency key must span BOTH
  providers. If each holds its own, a payment attempted on the primary and
  retried on the secondary charges twice. Assert exactly one charge.
- **A-63 split-brain.** The primary succeeds but the response is lost, so the
  secondary is invoked. Assert reconciliation detects the duplicate and resolves
  to a single ledger entry.
- **A-64 stale event after failover.** A late cancellation or capture from the
  dormant provider must not mutate live state. **This codebase already shipped
  that bug's cousin**: `reconcile-subscription` had to be made cross-gateway
  because a Razorpay-only version re-activated a stale Razorpay subscription
  after a user switched to Stripe. Test the specific scenario — switch gateway,
  then fire a stale cancellation from the old one.

Also A-68: where no fallback exists, assert cached data is served with an
explicit staleness indicator and never presented as fresh. That one is testable
today for Instagram metrics and is the cheapest partial win in this discipline.
